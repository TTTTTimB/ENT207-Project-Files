# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Project-specific direction

- Follow the provided `正大广场｜To B 六页.fig` and `正大广场｜To C 六页.fig`: warm ivory surfaces, restrained gold/brown accents, quiet editorial headings, and rounded white cards.
- Keep the customer and merchant experiences connected through the signed-in account's role and store detail links (the old manual audience switcher was removed by the login decision below). Preserve responsive navigation on narrow screens.
- Use local demo values only until the user supplies/authorizes API integration. Keep clearly labeled that values are simulated. Multi-floor indoor navigation is in scope (2026-11-04 user decision): `src/routeEngine.js` builds a walkable grid from each floor SVG and plans a journey — same-floor legs walk directly, cross-floor legs route to an elevator (preferring elevators, stairs as fallback), ride between floors, then continue on the destination floor. Shop outlines are obstacles and every walking step is validated against wall segments so routes never cut through walls. Start options include facilities and all merchants across floors; merchant lists are sorted alphabetically and the merchant group is listed first in the start panel. There is no top-level floor selector on the navigation page — floor filters (全部 + B1–10F) plus multi-select type filters (商户/电梯/出入口/楼梯) live inside the start/destination panels, and search accepts shop names or floor tokens such as `5F`/`5楼`/`5层`/`B1`, with an always-visible selected-item summary and clear control. There is no start/destination swap control. The route map has exactly two top-level modes — 「3D 地图」 and 「2D 地图」(no third 全览 button in between): 3D map (three.js, `src/Floor3DView.jsx` + `src/floor3dData.js`) contains a display-scope switch 行程楼层/全览 — 全览 highlights every floor uniformly (solid slabs + shop walls on all floors, no journey-floor distinction) while keeping the route; 2D map contains the per-floor switcher B1–10F. Orbit/zoom controls plus reset. A real corridor network and live positioning remain out of scope.
- Keep demo records isolated in `src/demoData.js`; adapt that module to API response data when the backend is ready.
- The site supports two data modes: demo data (default fallback, keeps the portable single-file build working offline) and database mode (when `/api/health` is reachable, `src/api.js` loads shops from the Express + PostgreSQL backend and the top badge shows 数据库已连接). Deployment steps are documented in `docs/deployment.md`; the PostgreSQL export lives in `database/mall_navigation_postgres.sql`. Keep the fallback path intact — never make the site depend on a running backend.
- Login gate + account binding (2026-11-05 user decision): the app opens on the login page and the signed-in account's role decides the workspace — customer → 顾客端, merchant → 商户工作台 scoped to the shops assigned to that account, admin → 商场管理工作台 with the extra 账号管理 page. There is no manual audience switcher anymore. Accounts are local demo accounts (`src/auth.js`): stored in `localStorage` under `superbrand.login-demo.accounts.v1`, session in `sessionStorage` (`superbrand.login-demo.session.v1`, 8h), passwords hashed with PBKDF2-SHA256 (600k iterations, salted, via WebCrypto), favorites per account in `localStorage` under `superbrand.favorites.<accountId>`. Demo accounts: `customer` / `merchant` (assigned 1F · DESCENTE 迪桑特) / `admin`, initial password `MallDemo2026`; the page is visibly labeled 本机演示版. Account updates bump `revision` and invalidate existing sessions. The login page, session bar, account admin and scoped merchant workspace styles live in `src/auth.css`. Keep the portable `file://` build working — localStorage/sessionStorage/WebCrypto are available there and must not be replaced by server-only auth without a fallback. Future real accounts should map to the `backend_account` / `account_shop` tables via API without changing the role → screen mapping (`SCREENS_BY_ROLE` in `src/auth.js`).
- Live deployment (2026-11-06, 0-cost stack): frontend <https://mall-navigation-demo.pages.dev> on Cloudflare Pages; backend <https://mall-nav-api.onrender.com> (Render Free, Docker, rootDir `mall-nav-api`); database Neon Free PostgreSQL (`neondb`, Singapore, imported `database/mall_navigation_tencent.sql`). The full deployment record, configuration, gotchas (Neon pooler `search_path` → SQL uses explicit `public.` prefixes; Render needs `PORT`/`0.0.0.0`; Cloudflare Pages needs Root directory `mall-navigation-site`, build `npm run build`, output `dist/client`, `VITE_API_BASE`; `NODE_VERSION` must be `22`) and maintenance steps live in `docs/deployment-free.md`. Render/Cloudflare auto-deploy on every push to `main`; database password is only in Render env vars, never in the repo.
- Home → shop detail → navigation (2026-11-11 user decision): on the customer home page, the mobile shop list highlights the map location and reveals a full-width action under the tapped name — 「查看「X」详情」 when the name matches a shop (opens the shop detail page, whose 「前往店铺」 goes to the navigation page prefilled), otherwise 「在店铺目录中查找「X」」 (opens the directory filtered by name). Desktop home supports the same flow via clicking a shop polygon or its name in the SVG's right-side shop list; shops are keyboard-activatable with Enter/Space. Matching (`findShopByName` in `src/App.jsx`) is normalized + fuzzy and prefers the current floor to avoid same-brand cross-floor mistakes. The desktop hint text and mobile hint text are rendered separately via `.hint-desktop`/`.hint-mobile`; styles for both live in `src/shop-mobile.css`.
